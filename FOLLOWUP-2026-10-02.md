## 7. FOUND AT 03:2x — why the deploy is blocked, and it is the same bug Cyrus reported twice

`check:analysis` now fails on **one console 404** and the gate therefore refuses to deploy the
basemap lightening. The URL is:

```
https://raw.githubusercontent.com/Cyruschu430/hk-city-monitor/live-data/ai_summary.json  ->  HTTP 404
aircraft.json -> 200   berth_vacancy.json -> 200   water_suspension.json -> 200
```

**Root cause.** `scripts/publish_live.py` force-pushes an ORPHAN commit: anything not in its temp
repo stops existing on the branch. `ai_summary.json` is written by `ai-brief.yml` twice a day, and
this collector runs every 10 minutes — so every city brief was deleted within ten minutes of being
published. The panel fell back to its committed snapshot and still rendered, which is exactly why
this looked like a UI bug twice ("City brief 都係見唔到").

**Fixed tonight** in `5ab1001`: `publish_live.py` now carries `ai_summary.json` forward from the
branch into the orphan commit before pushing (a 404 means the AI job has not run yet and is skipped;
any other failure warns and continues, because a refusing collector is a stale panel).

## 8. Morning correction — the AI brief diagnosis, and step 1 was unnecessary

**`OPENROUTER_API_KEY` IS already set as a repository secret.** The workflow's own environment dump
shows `OPENROUTER_API_KEY: ***`. It is absent from the VPS shell, which is a different thing and is
why a local run refuses. **Do not spend the morning on `gh secret set`.**

**Why every run fails — from the failed logs, not from theory:**

```
round 1 qwen/qwen3.8-27b:free: HTTP 429 "temporarily rate-limited upstream"
round 1 google/gemma-4-31b-it:free: HTTP 429
round 1 google/gemma-4-26b-a4b-it:free: HTTP 429
round 2: all three again  (and on 2026-10-01T14:10 one returned an empty body: "did not return JSON")
every model in the chain was unavailable -> exit 1
```

The free OpenRouter pool is saturated, so the brief has not been published for days. That is the
whole cause; nothing is broken in the workflow itself.

**The fix is more models in `MODEL_CHAIN`, or a non-free fallback** — the chain is
`scripts/build_ai_summary.py`'s `MODEL_CHAIN`, and the requirement is only that a candidate returns
JSON. Adding a cheap paid model would break the project's "no metered key" rule as written for data
sources; a brief twice a day is not a cost risk, but that is Cyrus's call, not mine.

**Schema gotcha, so nobody hand-writes a broken file.** `data/ai_summary.json` is NOT
`{tc, en, model}`. It is:

```json
{"generated": "...", "model": "google/gemma-4-31b-it:free",
 "provenance": {"generator": "LLM summary of published open data",
                "inputs": [{"file": "aircraft.json", "from": "live-data", "observed": 1790852103501}, ...]},
 "brief": {"tc": "...", "en": "..."}}
```

The panel reads `brief.tc` / `brief.en`. A file with `tc` at the top level renders as nothing, which
would look like a UI regression all over again. I attempted a one-off restore with Gemini and
stopped when the environment had no Google key — and the attempt is what surfaced this schema.

**Consequence:** the branch still has no `ai_summary.json`, so `check:analysis` still fails on its
404 and **the basemap lightening (`18e8d8e`) is still not deployed.** The app is unaffected: it falls
back to the committed `dist/data/ai_summary.json` snapshot, exactly as designed.
